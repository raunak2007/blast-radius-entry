# Blast Radius entry

Picks the sqlglot tests each patch can break, then packs them onto workers.

**Sample set (30 commits):** 94.4 s simulated, 0 misses, about 2.9 s of CPU. The starter scores 1210.5 s.

## How it decides

Every map comes from running sqlglot's own tests at the pinned commit (`eb11aec4`), which the track rules allow. No patch or answer file is used to build anything.

- **Comment-only hunks** (comments or blank lines outside strings) change nothing Python runs, so they select nothing.
- **A changed statement inside a function** selects the tests that executed it (per-test line coverage). For a statement spread over several lines, the function is compiled before and after the edit and only the lines holding changed instructions count (a jump whose target moved counts where it stands), so a short-circuited condition or an untaken branch on its own line doesn't pull in every test that ran the statement.
- **A changed class attribute, or a new method** selects the tests that used that class: the dialects it serves (and their subclasses), or the expression type and its subclasses.
- **A changed fixture or data file** selects the tests that opened it. That includes sqlglot's own sources: one test reads the `sqlglot/typing/*.py` files as text to see which module each imports its metadata from. A check runs patched imports but reads the unpatched file, so when a patch changes such a file's import statements that test stays selected unchecked.
- **A changed test file** selects the edited tests (or their class or file), judged on both sides of the edit: the statements it replaces or is put between in the old file, and the ones its added lines belong to in the new file (a `setUp` put right after another method belongs to neither neighbour and reaches the whole class). Module-level code of a test module also selects the tests of the test modules that import it, directly or through one another, and a class other test modules use selects the tests of those modules and of their importers (33 dialect test files take `Validator` from `test_dialect.py`: 1,020 tests), since its code runs in their tests. Shared files with no tests of their own (`tests/helpers.py`, `tests/__init__.py`) select every test, unless the edit leaves their code as it was (comments, layout).
- **Anything risky** runs every test: a patch that won't apply, a syntax error, a module-level change other modules import, config files, renamed or deleted Python files, a source file that no longer compiles or changes its declared encoding.

- **Imports are checked, not assumed to work.** An edit that runs while modules are imported (class- and module-level code, a function line the imports run, a comment line that lands inside a SQL template string) can make an import fail. Then every test of a test file that imports the module fails, and every test that loads it later (a dialect by name) fails when it does, whatever lines those tests ran at the pinned commit: coverage of the edited line says nothing about them. So for each such commit whose selection is short of every test, a forked child with the patched sources imports sqlglot, every sqlglot module, every dialect by name and the six test modules whose import runs sqlglot code (about 0.15 s of CPU; sqlglot's core, imported once from the pinned sources, is kept when the patch changes none of its files, as in the run checks). Anything that fails and didn't before (the pinned sources are imported the same way, once, only if some commit reports a failure), a child that crashes, or one that runs out of time selects every test; the import-time state check below reports a failed import the same way. Two kinds of edit are left alone: one confined to the body of a lambda that no import runs, and the literal value of a class constant that no import-time code reads. Of 700 single-token mutants on lines that run at import (drawn one random file at a time), 22 break an import; before this check the selection for them held as few as 35 tests, and now all 22 select every test. On 600 random code mutants, 9 break an import. A `#` comment line inserted into the DuckDB generator's ZIPF SQL template (a class-level `exp.maybe_parse`) stops that module importing and fails 1,110 tests under pytest: the selection was 437 tests and is now all of them.
- **A name that disappears selects every test.** When a module or class stops binding a name (a def renamed or removed, an assignment or import gone), other modules' imports of it fail and lookups of it raise, and coverage of the old lines doesn't say who relies on it. The checks that run the patched sources still apply.
- **A function whose names resolve differently counts as a whole.** If an edit changes the names a function's body binds, its parameters, its `global`/`nonlocal` declarations or whether it yields, lines the edit doesn't touch behave differently (a name read before a new assignment to it is an unbound local; a call returns a generator), so every test that entered the function is selected. An edit that adds or removes lines also has the new file compiled, since `ast.parse` doesn't report what only the compiler rejects.
- **The same code selects nothing.** When the hunks can only have changed layout (line ends, spacing, wrapping, trailing comments) or text inside string literals, the two syntax trees are compared with bare constant statements (docstrings among them) left out. If they are equal the file compiles to the same code, and nothing in sqlglot or its tests reads a docstring. A file whose mode alone changes selects nothing.
- **A file that isn't code or configuration and is replaced, removed or moved** (binary patches included) selects the tests that opened it under either name: the tests open their data files by name.
- **Configuration files** are judged by what pytest does with them, since the commits were labeled by running pytest from the checkout (on `PYTHONPATH`, nothing installed from it). pytest reads `pyproject.toml` as UTF-8 and TOML, stops on a file it can't parse, and uses only its `[tool.pytest]` tables, which the pinned file doesn't have: an edit that leaves it valid TOML without such a table selects nothing, any other edit selects every test. The root `setup.py` is never run or read by a test run (pytest only looks whether it exists), so an edit to it selects nothing. An edit to `pyproject.toml` or `setup.cfg` that only adds or removes comment and blank lines selects nothing (neither has a multi-line string at the pinned commit that such a line could land in); any other edit to `setup.cfg` selects every test. A `pytest.ini`, `tox.ini`, `setup.cfg`, `pyproject.toml` or `pytest.toml` at the root or anywhere under `tests/` selects every test, as does a `conftest.py`: pytest takes its settings and root from the first such file it finds going up from the paths it is given.
- **The two TPC query files are read case by case.** `TestExecutor.setUpClass` loads `tpc-h.sql` and `tpc-ds.sql` for the whole class, so all 60 of its tests open them, but only three use what was loaded: `test_optimized_tpch` (inputs and expected outputs) and `test_execute_tpch`/`test_execute_tpcds` (the meta lines and the input queries); `TestOptimizer.test_tpch`/`test_tpcds` read whole cases. Both versions of an edited file are split into cases the way the tests' own `load_sql_fixture_pairs` splits them (reimplemented on text; it agrees with the loader on all 26 fixture files of the pinned commit). While the edited file still loads into the same number of cases, a test is selected only if a part it reads changed: an edit to an expected output in `tpc-ds.sql` selects `test_tpcds` alone (4.2 s instead of 25.5 s), no edit to `tpc-h.sql` selects the 21 s TPC-DS test, and a comment or blank line the loader drops selects nothing. A file that no longer loads, or loads into a different number of cases, keeps every reader. Python under `benchmarks/`, `docs/`, `posts/`, `pdoc/` and `.github/` is read by no test and no build, and selects nothing.
- **A new file can change tests although nothing imports it.** The tests run with the repository root first on `sys.path`, so a new top-level module or package named like a standard-library or installed one hides it (a root `enum.py` breaks every test); a new package directory hides the module file of the same name beside it; a new `__init__.py`, `sitecustomize.py` or `.pth` file changes what gets imported; a new pytest settings file (`pytest.toml`, `pytest.ini`, ...) or `conftest.py` changes every run; a new `.so` or `.pyd` file is taken for a compiled module ahead of the source file of the same name; and a new module can have a name that an import at the pinned commit already asks for (`sqlglot/__init__.py` tries `sqlglot._version` and goes on without it; dialects load by name on demand), which is the case when its name stands as a whole word in sqlglot's sources or the tests (for a file under `tests/`: in an import statement of a test file). All of these select every test. A new module in a folder whose sources a test reads (`test_typing` reads every module of `sqlglot/typing`) selects that test. Any other new file selects nothing.

- **Cheap selections are checked by running them.** When the selected tests cost less to run than to schedule (each worker costs 2 s), they run on the patched sources in a forked child (patched imports, process pools forked and capped at 2 workers) and the ones that pass are dropped. Anything that crashes, times out or can't run faithfully stays selected. A check may use 4 s of CPU plus its test files' setup allowance plus four times its tests' recorded time (`RLIMIT_CPU`, which each process-pool worker it forks inherits on its own count): an edit can make a test loop for ever (a parser that stops advancing), and until the check is stopped the loop runs on CPU the score pays for. The wall-clock limit is 10 s looser, so a check that is only waiting for a busy machine is not cut off. Each check is its own process group, killed whole when the check ends, so pool workers a killed check leaves behind stop too. The parent freezes its heap before forking (`gc.freeze()`), so a check's collector never walks, or copies the pages of, the maps and imports it inherited, and checks collect young objects less often. The parent also imports sqlglot's core once (the 37 files a bare `import sqlglot` loads). A check whose patch changes none of them keeps that copy and imports the rest, the patched module included, as before; any other check forgets every sqlglot module and imports all of it again.
- **What a check costs is estimated per test.** `test_optimizer`'s heavy tests (most run fixtures through a process pool, and they are the ones an edit most often breaks) are charged 3.7 times their measured check CPU, so they are rarely worth running; the file's other tests cost what they take. `TestExecutor`'s `setUpClass` loads the TPC-H and TPC-DS tables (1.1 s). A check skips it when the commit changes nothing but ordinary function code outside `sqlglot/executor/table.py`, the one file `setUpClass` runs code from, and none of the tests being checked touches what it builds (told from the test file's source). Then `setUpClass` does exactly what it did before, so it can't fail, and those tests run the same without it.

- **Fixture-driven tests are checked on the entries an edit can reach.** `test_optimize`, `test_simplify`, `test_annotate_funcs` and 26 other tests loop over the entries of a `.sql` fixture, and they cover so much code that most edits select one of them. `tools/build_fixture_cov.py` records, per entry, the lines its processing runs: in an ordinary run of the test, and alone in a fresh process, so code that only runs the first time something is used counts for every entry that needs it. When a commit changes nothing but ordinary function code, and at most a fifth of a test's entries can run a changed line, the check runs the real test with its fixture loader yielding only those entries. Every other entry never runs changed code, so it does what it did at the pinned commit, where the test passes. On the sample this drops `test_optimize` after 1 of its 94 entries.

- **Class-attribute edits are narrowed** to the tests that read the attribute, ran the edited lambda, or built the `exp.X` keyed by the edited dict entry. For the parser's function tables, an entry is narrowed to the tests that looked up its old or new name unless an import-time parse looks that name up or something writes it at runtime (`tools/build_key_level.py`). Tokenizer `KEYWORDS` entries likewise, unless the key is popped or checked at import time, looked up by a tokenizer while modules import, or has a space or single-token character (the keyword trie) (`tools/build_keywords_level.py`).

- **The 21 s TPC-DS test is replayed instead of run** when every change is ordinary function code in `sqlglot/` that the test's table setup doesn't run. Only the queries whose recorded coverage reaches a changed line are replayed, each checked by what the line can affect for that query. If it only runs in parsing, `optimize()` or the duckdb transpilation, the optimizer output is compared. If it also runs in the debug-log rendering `execute()` does next (whose text is dropped), that rendering must not raise or change the expression. If it runs in planning or execution, the full result is compared. The duckdb transpilation is always compared. An optimizer output that differs only in node metadata counts as unchanged for queries whose rendering, planning and execution never read metadata (all 57, checked by `tools/build_tpcds_meta.py`). Any difference, error or timeout keeps the test, and the replay only happens when its estimated CPU is well under the time it saves (at most 0.8 of it when only optimizer outputs are compared, 0.66 when queries run to the end). The replay also stops once it has used 3 s plus six times the recorded CPU of the queries it has started, so an edit that makes a plan explode fails fast instead of using the whole budget. The tables' rows stay pickled, per table, until a query runs to the end (`tools/pack_tpcds.py`): a replay that only compares optimizer output never loads them.

- **Recorded operands** (`tools/operand_plugin.py`, a second profiled run of the suite at the pinned commit). Every single-operator comparison in `sqlglot/` is compiled to record the operands it sees per test, and every module- or class-level dict literal is wrapped when it is created, so its reads are recorded per key even through a reference another object keeps (the tokenizer holds on to `NUMERIC_ESCAPES`), and reads made while modules import are recorded so those keys are refused. An edit that only swaps a comparison's operator or changes a literal operand is re-evaluated on those operands, and tests whose recorded results can't change are dropped. A comparison that also ran while modules were imported is judged the same way once the import-time state check (below) has found that nothing those imports built changed; before, such an edit kept every test that ran the line. `len(result) > 1` in `parse_one` runs in 1,472 tests and at import: with the literal changed to 2 it selects the two tests that parsed more than one statement, and the run check leaves the one that fails. Of the 346 single-token mutants on such lines, 14 get a smaller selection; those 14 were run under pytest against the wider selection (the whole suite where that was most of it) and every failing test is still selected. A one-line edit to one dict entry's plain value, where our own per-name key index gives up, selects the tests that read that key or read the dict in bulk. Both files are packed per source file so a run unpickles only what its commits touch.

- **Import-time effects are judged per instruction.** A statement in a function that also runs at import (a builder called in a class body) only widens the selection to everything importing the module when a changed instruction itself ran at import. The body of a lambda or closure such a builder returns never runs then, so an edit there selects the tests that ran it. Every line a fresh process runs while importing all of sqlglot and its tests is in the map's import-time lines, which is what this relies on.

- **A changed def line** (a default value, say) selects the tests that ran the function, and, when its body also runs while modules are imported, everything an import-time change selects: a default the import-time template parses take differently can stop a module importing at all. Overload stubs (`...` bodies) are exempt.

- **Import-time state is checked, not assumed changed.** When a changed function line also ran while modules were imported (the parser runs while the DuckDB generator parses its SQL templates), the selection is normally widened to everything importing them. If the narrower selection would save at least 3 s over what the wide one costs after its own run check (a wide selection that is cheap to run is just run), a fresh interpreter (fixed hash seed, CPU and memory capped) imports every sqlglot module and the six test modules whose import runs sqlglot code, once with the patch and once without, and fingerprints all module and class state: values, containers, expression trees, function defaults and closures, the objects they reach, and which imports fail. Code is left out, since what runs later is what coverage decides; tuples are compared by value and class-only sequences by name, since their identity and order follow memory addresses. Equal fingerprints mean the edit only matters where its lines run in tests, and the commit is planned (TPC-DS replay included) as ordinary function code. The unpatched sources are imported by one process for all the commits that need the check; each commit's set of left-out bindings is fingerprinted in a fork of it, so no fingerprint sees what another one touched. The fingerprint leaves out what only typing introspection reads: annotations, and what a `TypedDict` records about its keys (`__total__`, `__required_keys__`, `__optional_keys__`), so flipping `total=` on one of `sqlglot/_typing.py`'s argument dicts selects nothing instead of every test (they are plain dicts at run time, and neither sqlglot nor its tests introspect them).

- **Decorators, base classes and lambdas in class or module code** go through the same check instead of selecting every user of the class or module. A lambda's body is code, which the fingerprint leaves out, so an edit inside one selects the tests that ran the lambda. Plain value edits (a constant, a call's arguments) skip the check, since they almost always change what the import builds. Each function's fingerprint includes its def line in the unpatched numbering, so it matters which of two same-named defs got bound, but lines a patch inserts above a def don't.

- **An edit confined to a lambda's body needs no check at all**, wherever the lambda sits in a class- or module-level statement: in a dict nested in a dict value (the type annotators, `exp.If: {"annotator": lambda ...}`), in a call's argument (`null_if_any(lambda ...)`), in a comprehension. The statement is compared before and after with that one body taken out; if the rest is the same tree, evaluating it builds the same objects except for the code the body runs, so only a test that runs the body can tell. It selects the tests that ran the lambda's lines and is planned as function code (fixture-entry checks and the TPC-DS replay apply; the replay's rule that a changed line must not run in the test's setup is for function code only, since a lambda's lines count as run whenever its module was imported by then). Before, a type annotator's entry selected every test that built its expression type, the 21 s TPC-DS test often among them. The exception is a lambda whose body ran while modules were imported: the DuckDB generator and Hive's type annotations parse SQL templates at import, which runs 24 entries of the parser's lookup tables (`"COUNT"`, the literal parsers, `exp.DataType`). `tools/build_import_lambdas.py` lists them from the pinned commit, and an edit inside one goes through the import-time check instead, since it can change what those imports built for tests that never run the lambda themselves.

- **`test_lazy_load`** is the one test that starts a second interpreter, and all that interpreter does is `import sqlglot`. So it is only selected when a patch changes one of the files that import loads, or something that isn't plainly another sqlglot module or a file under `tests/`.

- **A changed class constant** (an UPPER_CASE class attribute's literal value, for names no import-time code reads, or, when some does, after the import-time state check finds nothing changed but that constant) selects the tests whose reads of it resolved to that class: `tools/attrs_plugin.py` replaces every such constant with a descriptor that returns the same value and records the reader, so a read through a subclass that doesn't override it counts, and one through a subclass that does doesn't. `ClickHouseGenerator.TABLE_HINTS` goes from the 736 tests that read any `TABLE_HINTS` to none.

- **A flipped boolean flag is narrowed to the reads where it mattered.** `tools/attrs_plugin.py` also files each read of a class constant under the line that made it, and lists every line an exception surfaced on. `tools/build_attr_owners.py` then looks at each reading line in the pinned sources: where the flag only gates the rest of a condition (`if self.FLAG and <rest>:`, or `not self.FLAG and ...`), the later operands do nothing but compute a value (names, comparisons, `isinstance`, `args.get`) and none of them ever raised in the recorded run, the flag's value mattered only where the rest came out true, and then the test ran the first statement of the `if` body (or, outside an `if`, the operand after a boolean-valued one). So when a commit's one code change flips such a flag to the value that stops the condition, each of those reading lines keeps only the readers that ran those lines; a read anywhere else keeps all its readers. The test whose run would first differ is always kept: up to that read both runs are the same, and at that read it is either one of the kept readers or the rest was false and nothing differs. `BaseParser.SUPPORTS_TABLE_QUERY = True` is read by 521 tests and selected 1,584 (its reads also run at import); it gates `_curr is TABLE and (...)` and now selects the 2 tests that got past the first comparison, one of which fails. 27 reading lines qualify; the 16 single-token flips this changes were all run under pytest against the wider selection (the whole suite for the two that selected most of it): every failing test is still selected.

- **A changed default value** selects only the tests in which some call left that parameter out (`tools/defaults_plugin.py`, sys.monitoring on every module- and class-level function with defaults; an explicit argument that is the very same object counts as left out).

- **Checks run on commits that also change a data file** (a fixture next to a code edit), on the tests that never open the changed file; its readers stay selected. The TPC-DS replay, the generator memory check, the executor checks without `setUpClass` and the fixture-entry checks apply to such commits too, for tests that never open the changed file: on 150 mutants with a code edit, a fixture edit and a comment this cut 143 s, most of it from 12 TPC-DS replays. The import-time state check runs for such commits as well: nothing reads a fixture while modules import (a file read outside tests counts as configuration and runs everything), so the check sees the same imports with or without the data file's change. On 188 mutants whose state check passes, each paired with a fixture edit, every answer holds the code-only answer plus the fixture's readers, and the total simulated time is exactly that of those two sets together (1,414 s; 3,838 s before).

- **`test_max_nodes` (28.8 s, the slowest test) is checked on prefixes of its statement.** The test parses 10,000 copies of a depth-100 comparison against node limits of 1,000,000 and 50,000. At the pinned commit that statement makes 1,000,001 counted nodes, so the first limit trips on its very last node. When a selection holds the test and dropping it would pay for the check, a forked child on the patched sources runs the test's small asserts as written, counts the nodes of 10, 40 and 160 copies (the count must be exactly linear and put 10,000 copies past 1,000,000), checks that a limit one below a prefix's count trips on that prefix's last node with the error the test looks for (and that a limit equal to the count doesn't trip), and that a prefix long enough to pass 50,000 nodes raises mid-statement. Any doubt, any exception, an import error of the test's module, or more than 4 s of CPU keeps the test; a patch to `tests/test_parser.py` itself is never checked this way. It costs about 1.2 s of CPU against the 7 to 26 s the test adds to a selection. What it rests on: an edit that leaves 160 copies exactly linear treats the next 9,840 the same (nothing in the tokenizer or parser depends on how far into a statement it is). The real test was run on 111 single-token mutants of lines it executes, the node-limit code and the error path among them: it fails on 5, the check kept all 5, and it passes on every mutant where the check dropped it. On 600 random mutants the test stays in 2 selections instead of 14, 4% off the simulated total.

- **A TPC-DS replay child may allocate at most 1.25 GB beyond what it inherits**, so an edit that makes one query's intermediate results explode fails its own replay instead of exhausting the run's 4 GB. (Test checks are left uncapped: duckdb reserves far more address space than it uses.)

- **Code that runs while other modules import** (the trie builder every tokenizer class calls, the error formatter a dialect's import-time parse reaches) selects every test that uses those modules, a module whose import imports them, or imports one of them while it runs (`from sqlglot.dialects import X` inside a test) (`import_users.pkl.gz`), and the generator's first-use dispatch table selects every test that builds a generator.

Tests are packed longest-first, trying 1 to 8 workers and keeping the cheapest.

## Files

| File | What it is |
| --- | --- |
| `selector.py` | The program the scorer runs (stdlib only) |
| `blast_map.pkl.gz` | Coverage, file reads, and dialect/expression usage per test |
| `tpcds.pkl.gz` | Per-query coverage, CPU and pristine outputs of `test_execute_tpcds`, plus its tables (`tools/build_tpcds.py`, then `tools/build_tpcds_ctx.py`, which records each query's coverage from a fresh pool worker, split by what checks each part) |
| `fixtures.pkl.gz` | Per fixture-driven test and fixture entry, the lines its processing runs (`tools/build_fixture_cov.py`, `tools/pack_fixtures.py`) |
| `attr_owners.pkl.gz` | Per class constant, the tests whose reads resolved to it, by reading line, with the lines that show a gating flag mattered (`tools/attrs_plugin.py`, `tools/build_attr_owners.py`) |
| `defaults.pkl.gz` | Per function and defaulted parameter, the tests in which a call left it at its default (`tools/defaults_plugin.py`, `tools/build_defaults.py`) |
| `operands.pkl.gz`, `dictreads.pkl.gz` | Per test, the operands each comparison saw and the keys each module/class-level dict literal gave out (`tools/operand_plugin.py`, `tools/build_operands.py`, repacked by `tools/build_lazy.py`) |
| `import_users.pkl.gz` | Function-body lines that run while other modules are imported, with the modules that affects (`tools/build_import_users.py`) |
| `sqlglot_src.tar.gz` | The pinned commit's Python sources, which patches are applied to |
| `tools/` | Rebuilds both data files from the pinned commit (`tools/build_map.sh`) |
| `Makefile`, `score.py`, `requirements.lock` | From the starter kit, unchanged |

The build downloads the base image, the packages in `requirements.lock` from PyPI, and sqlglot's repository at the pinned commit (for its test fixtures); nothing else.

This branch is a single commit of the v25 tree, so a clone stays well under the 20 MB limit (earlier versions of the data files add up). The history is on branches `v6` to `v24` of this repository; v25 continues from `v24` (`b929b8d`).

## Test locally

Copy the kit's `sample/` folder in (it's git-ignored), then:

```sh
make sample
```
